Task 2.2: Custom Rule Engine (JSON Rule DSL v1)

UPDATED Phase 2

Assignee: Temujin   Depends on: Task 2.1

Objective: Allow organizations to define custom compliance rules beyond the built-in patterns. Evaluate rules in the screening pipeline. v2 retitle: v1 ships the JSON rule DSL below; Cedar/OPA is a separate v2 decision spike, scheduled only when customers articulate rules the DSL cannot express.

JSON Rule DSL (v1)

{
  "name": "block-ssn-in-prompt",
  "condition": {
    "field": "prompt",
    "match": "\\b\\d{3}-\\d{2}-\\d{4}\\b",
    "type": "regex"
  },
  "action": "block",
  "reason": "SSN detected in agent prompt"
}

Evaluate after Phase 3 (LLM analysis), before returning final verdict. Log custom rule hits in ScreeningEvent metadata.

Acceptance

  • Custom rules can be created, listed, updated, deleted; scoped to API key / organization
  • Rules are evaluated in the screening pipeline; hits appear in audit trail with rule name and reason
  • v2 (ReDoS hardening): customer regex compiled with a linear-time engine (RE2 or equivalent) — no backtracking engine ever evaluates customer patterns
  • v2: per-rule evaluation timeout ≤ 5ms; max 100 rules per key; rules rejected at create time if they fail compile or exceed complexity limits
  • v2: total custom-rule stage adds ≤ 10ms p95 to the pipeline (load-tested in acceptance)

Task 2.3: Enforcement Dial (monitor → warn → block)

NEW Phase 2

Assignee: Temujin   Depends on: Task 2.1   Gap: #2 — the X5 monitor→enforce chasm; the single highest-leverage lever in the plan

Objective: Add enforcementMode: monitor | warn | block to ScreeningPolicy. In monitor, the full pipeline runs and verdicts are recorded but nothing is blocked; in warn, responses carry the verdict annotation; in block, current behavior. Every event in monitor/warn records the counterfactual wouldBlock: true/false so customers can see exactly what blocking would have done before they turn it on.

Acceptance

  • Mode honored end-to-end (pattern, structural, LLM, custom-rule, and Phase 8 governance verdicts all respect the dial)
  • Migration: existing keys default to block (preserves current behavior); newly created keys default to monitor
  • ScreeningEvent gains wouldBlock + enforcementMode columns; API responses include both
  • Dashboard Overview: dial control + "would have blocked N in last 7d" counter + estimated false-positive rate (from override/feedback signals)
  • Dial changes create PolicyRevision + AuditEvent

Standing admin requirement (implemented by this phase): Parse admins control (a) which volumes of data each agent can access — Task 8.1 registers data sources with classifications and grants per-agent access; (b) how much data an agent can move — Task 8.4 caps records/bytes per request and per day; (c) what may be shared externally — Task 8.3 evaluates every egress against destination allowlists and a classification × destination matrix. Task 8.1: Data Source Registry & Per-Agent Access Grants

NEW Phase 8

Assignee: Temujin   Depends on: Tasks 1.1, 2.3   Gap: #5 + admin data requirement — G4 foundation

Objective: Admins register the data volumes agents may touch and grant access per agent. Ungranted access is a policy violation enforced through the dial.

Models

DataSource      — id, name, kind (filesystem | database | api |
                  vector_store | document_collection),
                  classification (public | internal | confidential | restricted),
                  owner, orgId/apiKeyId
AgentDataGrant  — agentId, dataSourceId, access (read | write | readwrite),

Enforcement

  • Referenced source not granted to the agent → data_access_violation flag; verdict follows the enforcement dial (monitor: recorded; block: request blocked)
  • Unknown/unregistered source IDs → unregistered_data_source flag (surfaced in Active Holes)
  • Expired grants stop working at evaluation time; grants and revocations create AuditEvents

Acceptance

  • CRUD for data sources and grants (compliance_admin to write); grants visible per agent and per source
  • Violation events appear in the audit trail with source, classification, and agent
  • Grant checks add ≤ 3ms p95 (cached grant table, 30s TTL)

Task 8.3: Egress Destination & External Sharing Controls

NEW Phase 8

Assignee: Temujin   Depends on: Task 8.1   Gap: #5 + admin data requirement — the "share externally" half; S2 egress control

Objective: Admins define where data may go. Every output/intended action with an external destination is evaluated against egress rules before the verdict.

Model

EgressRule — scope (org | key | agent), destinationPattern (domain, email
             domain, webhook URL prefix, or "*"),
             maxClassification (public | internal | confidential | restricted),
             action (allow | require_approval | block), priority

Logic

  • Destination extracted from intended_action metadata and screen-output content (URLs, email addresses)
  • Data classification of the flow = max(classification of granted sources touched this session, content-detected sensitivity from the existing sensitive-data layer)
  • First matching rule wins by priority; default templates shipped: "restricted never leaves" (restricted → any external = block), "confidential needs approval" (confidential → require_approval via existing approval workflow)
  • require_approval uses the existing HMAC approval flow; approvals route via 3.3 channels

Acceptance

  • CRUD for egress rules (compliance_admin); rule test endpoint ("would this destination + classification pass?")
  • Egress verdicts enforced through the dial; blocked/approval-pending egress visible in audit trail with destination + classification
  • Default templates installable in one click from the dashboard

Task 8.4: Data Volume Budgets & Bulk-Movement Detection

NEW Phase 8

Assignee: Temujin   Depends on: Task 8.1   Gap: #5 + admin data requirement — the "how much" dimension; closes C11 (agent-scale insider misuse)

Objective: Caps on data quantity, because an agent that may read a source may still not siphon it. Budgets per (agent × data source) and per agent overall: maxRecordsPerRequest, maxRecordsPerDay, maxBytesPerDay.

Logic

  • Requests report records_accessed / bytes_accessed in metadata (SDK auto-fills for wrapped tool calls where countable; self-reported otherwise — v1 honesty note documented)
  • Sliding-window counters in Redis (reuses the BullMQ Redis); 80% of budget → alert via 3.3; 100% → verdict per dial
  • Budget breaches always alert regardless of severity filters (wired in 3.3)

Acceptance

  • Budgets configurable per agent and per (agent × source); current usage visible via API and dashboard bars
  • Counter accuracy verified under concurrent load; counters survive restart
  • Breach events carry agent, source, window usage, and budget in the audit trail and SIEM stream

Phase 10: Audit-Grade Attribution (Gap #3) NEW

Every compliance claim in Phases 1–8 currently rests on caller-supplied agent_id. Phase 10 makes identity verifiable: signed requests turn the registry from self-reported to attested, and screening receipts let any internal resource demand proof-of-screening — the first prevention-rung primitive.

Task 10.1: Signed Agent Identity

NEW Phase 10

Assignee: Temujin   Reviewer: Mongke (crypto review)   Depends on: Tasks 1.1, 9.1

Objective: Registration issues an ed25519 keypair per agent. The SDK signs each request (timestamp + body hash); Parse verifies and stamps events attributionVerified: true. Spoofed agent_ids become detectable instead of silent.

Acceptance

  • Keypair issued at registration; private key delivered once, never stored server-side; rotation endpoint (POST /v1/agents/:id/rotate-key)
  • Signature verification adds ≤ 2ms p95; clock-skew window ±60s; replay rejected (nonce cache)
  • Registry and audit trail visually distinguish verified vs self-reported agents; policy option: treat unverified agents per the dial
  • Events from a registered-but-unsigned agent_id raise an attribution_mismatch flag (possible spoof) and always alert

Task 10.2: Screening Receipts v1

NEW Phase 10

Assignee: Temujin   Reviewer: Mongke   Depends on: Task 10.1 (signing infra); builds on existing approvals HMAC/TTL machinery

Objective: Screening responses can include a short-TTL signed receipt binding verdict → action hash → agent → policy revision. Downstream resources verify receipts and refuse unscreened requests — enforcement distributed to the things worth protecting.

Receipt Claims

{ "sub": agentId, "act": sha256(canonicalized action/input),
  "verdict": "allow", "policyRev": revisionId, "mode": "block",
  "iat": ..., "exp": iat + 60, "sig": ed25519 }

Acceptance

  • Receipts issued on request (include_receipt: true); JWKS endpoint publishes verification keys (asymmetric — verifiers never hold signing secrets)
  • Verifier middleware shipped for Express + FastAPI (~50 lines each, MIT-licensed) + an MCP-server wrapper demo that rejects tool calls without a valid receipt
  • Receipt verification is fully offline (no callback to Parse) — verify sig, hash match, freshness, verdict
  • Docs: "lock a resource behind proof-of-screening" quickstart

Phase 11: Security-Review Readiness (Gap #4 — C17) NEW

Phases 5–7 create a product sold to security teams — who send questionnaires before purchase orders. The control plane must out-comply its customers. This phase runs in parallel from the moment Phase 5 starts.

Task 11.1: Platform Hardening

NEW Phase 11

Assignee: Ogedei (ops) + Temujin   Reviewer: Mongke   Depends on: Tasks 1.1, 2.2, 5.1

Deliverables

  • compliance_admin scope enforced across all write surfaces added by this plan (registry, rules, SIEM/alert config, grants, egress, budgets, freeze); scope audit test that walks every mutating route
  • Rate limits on all new write endpoints; request-size caps on rule/grant bodies
  • Verify 2.2's RE2/timeout guarantees under adversarial rule corpus (ReDoS test suite in CI)
