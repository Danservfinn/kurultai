Phase 13: GTM Platform Build (Parse repo)

Task 13.1: Scoping Form & Lead Intake (/implement)

BUILD Phase 13

Assignee: Chagatai (UI/copy) + Temujin (schema review only)   Reviewer: Mongke   Depends on: 0.1 (migration infra)   Est: 4d

Objective: The GTM plan's single-input qualification tool: a public SSR intake form whose output feeds both the proposal and the eventual Parse configuration.

Models (new migration)

Lead              — id, email, name, company, source (form | magnet | manual),
                    status (new | nurturing | call_booked | scoped | quoted |
                    won | lost | unsubscribed), createdAt
ScopingSubmission — leadId, agentsInUse (claude_code | openclaw | hermes |
                    langchain | crewai | custom)[], agentCount, endpointCount,
                    toolsCallable[], dataSensitivity (public | internal |
                    confidential | regulated), complianceStandards[],
                    siemPlatform, timeline, budgetBand, notes

Steps

  1. SSR page in src/routes/public.ts pattern at /implement — form mirrors the GTM scope factors table exactly
  2. Honeypot field + per-IP rate limit (5/hr) + server-side validation; no CAPTCHA (agencies hate friction)
  3. On submit: persist Lead + ScopingSubmission, fire operator notification through the existing gateway (Telegram), create AuditEvent lead.scoping_submitted
  4. Confirmation page sets expectations: "implementation plan + quote within 1 business day"

Acceptance

  • Form live and mobile-usable; submission → operator notification in < 60s
  • Spam controls verified (honeypot drops, rate limit 429s)
  • No compliance standard implies certification: form copy says "standards you need to align to," never "we are certified"

Task 13.2: Quote & Proposal Generator

BUILD Phase 13

Assignee: Chagatai + Temujin (pricing-table review)   Depends on: 13.1   Est: 3d

Objective: Deterministic pricing engine over ScopingSubmission → draft implementation proposal + quote. Operator reviews before anything is sent — the generator drafts, never sends.

Logic

  • Tier mapping from the GTM scope-factor table (agents, endpoints, tools, standard, SIEM count) → $3K / $8K / $15K band + line items; config lives in src/lib/product-facts.ts so pricing has one source of truth
  • Proposal draft (markdown → SSR/PDF): scope, deliverables per 13.8 runbook stages, timeline, required subscription attach (Team now; Compliance tier when 7.3 gates pass), assumptions, exclusions (explicitly: no HIPAA/FedRAMP certification claims)
  • Quote states the v1 multi-client pattern: one Parse org/API key per end-client, held by the agency

Acceptance

  • Same submission always produces same quote (deterministic, versioned pricing config)
  • Operator approval step recorded via AuditEvent before any proposal is marked sent
  • Lead status transitions (scoped → quoted) tracked for 14.3 funnel metrics

Task 13.3: ESP Integration + Nurture Sequence

BUILD Phase 13

Assignee: Ogedei   Reviewer: Mongke (deliverability + compliance)   Depends on: 13.1, 15.2 (domain auth)   Est: 5d

Objective: The autonomous middle of the funnel: transactional + nurture email with real deliverability and real consent hygiene.

Steps

  1. ESP integration (Resend-class API) behind a thin src/lib/email/ adapter; all sends through BullMQ (reuses 3.2 worker patterns: retry, no loss, graceful shutdown)
  2. Double opt-in for magnet downloads; List-Unsubscribe + one-click unsubscribe; suppression list enforced at the adapter layer (nothing can email a suppressed address)
  3. 5-email nurture from the GTM plan (prompt injection 101 → why compliance blocks agents → how Parse works → case study → book a call), sent 2–3 days apart; templates versioned in repo
  4. EmailEvent model: queued/delivered/opened/clicked/unsubscribed per lead, feeding 14.3

Acceptance

  • Test lead traverses the full sequence on staging with correct spacing; unsubscribe halts sequence within one send cycle
  • SPF/DKIM/DMARC verified passing on the sending subdomain before first real send
  • Volume ramp respects the 15.2 warm-up schedule (hard cap per day, config-driven)

Task 13.5: Demo Tenant with Labeled Synthetic Data

BUILD Phase 13

Assignee: Ogedei   Depends on: 1.1, 2.3 (M1); enrichment after 8.1–8.5 (M3)   Est: 2d + 1d enrichment

Objective: Every sales demo runs on a deterministic, clearly-labeled synthetic tenant — preserving the repo's non-claimable-metrics discipline while giving the "show, don't tell" dashboard moment.

Steps

  1. Seed script: demo org, 7 registered agents (incl. one OpenClaw instance and one Hermes profile fleet), ~2,000 screening events across categories/verdicts/trends, 2 frozen-agent incidents, active-holes examples
  2. UI banner on demo org: "SYNTHETIC DEMO DATA" — non-removable for that org id
  3. Nightly reset cron; deterministic seed so screenshots/recordings stay reproducible
  4. Post-M3 enrichment: data grants matrix, egress rule hits, volume-budget breach, approval-matrix pending item

Acceptance

  • One command rebuilds the tenant; dashboard walkthrough script (13.8) runs against it without manual setup
  • Demo data never mingles with real metrics endpoints (org-scoped isolation test)

Steps

Task 13.8: Implementation Delivery Kit

BUILD Phase 13

Assignee: Kublai + Chagatai   Depends on: 13.2; runbook stages reference M1–M2 features   Est: 2d

Objective: The $3K–15K engagement as a repeatable, cappable process — the Lieben "cap parallel builds" principle applied to Parse itself.

Deliverables

  • Delivery runbook per tier: kickoff → client org + API keys created (one org per end-client, agency-held — the documented v1 multi-client pattern) → agent registration → policy config → dial staged (monitor, counterfactual review with client, then block) → SIEM connect → CISO dashboard walkthrough (against 13.5 script) → handoff doc + first evidence export
  • Concurrency policy: max 3 concurrent implementations; queue beyond that with stated lead times
  • Handoff template: what was configured, what the client owns, upgrade path (Compliance tier, org claim)
  • Case-study capture step baked into the final milestone (metrics snapshot + quote request)

Acceptance

  • A full dry-run delivery executed against the 13.5 demo tenant end-to-end from the runbook alone
  • Each stage has a time budget; bottom-tier total ≤ 5 working days of effort (validates the margin claim or corrects it with data)
